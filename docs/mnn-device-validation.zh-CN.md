## 2. 使用合成消息复现

1. 按 [评测样例说明](../tests/ai-summary/fixtures/README.md) 选择案例，记录样例版本/commit、案例 ID 和对应预期事实。只用合成内容，在测试者自有的隔离测试群/Topic 中手动准备数据，不把真实聊天混入样本。
2. 分别准备 **20、100、300 条有效短文字消息**和长文本集合。需要填充时使用固定的合成闲聊，并保存组成清单及顺序；不要把参考答案发送进群。记录条数、总字符数、最长消息字符数和发送者/回复关系。Telegram 消息长度限制可能导致拆条，以实际发送后的有效条数为准。
3. 每轮使用独立测试范围，确认消息均已发送成功。记录样例消息 ID 与 Telegram 原消息 ID 的对应关系；直接总结不再发送 `[mN]`；独立追问的编号以本次选取顺序为准，不能直接拿样例 ID 当客户端引用。普通群、可读频道、受保护群、具体 Topic 和论坛全部话题至少各执行一次；在相邻 Topic 放置可识别的合成消息，检查具体 Topic 隔离及全部话题覆盖。
4. 在 MNN Chat 加载记录中的模型、启动 API，再切换到 Telegram。使用该 APK 已提供的连接测试功能（如有）执行不含聊天内容的短请求；否则直接执行 20 条样例总结。记录实际鉴权和回复，不能仅凭 `/models` 可访问判定 Chat 请求通过。
5. 手动填写本次合成测试的核心要求，选择最近 N 条并开始总结；记录实际应用的要求，不能沿用旧版空 Prompt／默认三栏预期。保存实际纳入数量／范围、界面首尾消息 ID、开始与完成时刻及事实核对证据；核对最新标记消息是否纳入，新直接结果没有可点击来源链接。独立追问或带来源链接的旧历史另测引用定位，包括当前未加载到屏幕的消息。ID 有空位不等于漏消息，须结合媒体及筛选规则判断。不要将摘要自动发送回群。
6. 对每个基线场景记录一次明确标注的模型初载后首轮，再在相同条件下至少重复 3 轮。明确计时是否包含模型加载；不把“已加载模型后的首次请求”称为模型冷启动。变更后台状态、参数或模型后另起一行。
7. 按下表单独执行生命周期和失败用例，再逐条核对预期事实。只保留必要的合成数据证据；日志不得包含 API Key。任何不可测指标均填“未测 + 原因”，不得用估算值补齐实测。

针对本轮反馈，另外准备固定的 **10 条合成文字消息**，分别使用普通和流式模式、`2000` tokens／`32000` 字符预算执行，逐次记录实际请求及结束原因。合成消息长度与原反馈未必相同，这是受控对照，不能直接称为原故障复现；只有相应条件下实际再次发生才记录为复现。

长文本至少包含一个可完成的分块/合并案例，并将关键决定、否定或任务转交放在跨块位置；另外准备超出已确认客户端输入预算的案例，验证明确失败、没有静默截断。字符数不等于 token 数；服务端上下文超限要单独测试，不能用客户端预算错误代替。

- **功能成功**：按请求范围读取消息，完成本轮摘要，界面无崩溃/ANR，范围说明与实际覆盖一致。新直接结果不要求引用且没有来源跳转；独立追问／旧历史的引用另验正确定位。成功不自动代表事实正确或性能达标。
- **质量通过**：逐项匹配案例标注的关键事实和支持消息；区分建议/决定、否定/改口、争议/共识、任务转交，保留跨段关系，无结论或无待办时不编造。不能只凭输出包含引用或三个标题判定。

- **取消通过**：客户端取消行为符合 L04–L06；另列服务端停止推理的实测结论，不合并为一个通过项。
