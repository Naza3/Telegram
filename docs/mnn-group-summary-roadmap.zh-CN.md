# Telegram 本机 AI 群聊总结实施计划

本计划用于逐步完善 Telegram 安卓客户端中的 MNN 群聊总结，目标是让用户快速补齐群聊进度、按自己的关注点总结，并核对结论依据。优先完成真机诊断、自定义 Prompt、可见进度和增量总结，再扩展引用预览、性能优化、与我相关和摘要追问。

更新日期：2026-10-03。本文同时记录后续实施计划和已完成的代码验证；任务状态以勾选和验收记录为准，代码通过不代表真机已经验收。后续每次选择一个阶段或任务编号执行，完成后在本文记录证据和剩余问题。

## 当前基线

- 仓库：[Naza3/Telegram](https://github.com/Naza3/Telegram)，开发分支：`feature/mnn-group-summary`。

- 已有：最近 N 条／当日文字消息、群和 Topic 范围、话题／结论／待办、引用跳转、非流式请求、分块合并、取消、错误处理和按账号保存接口配置。
- 默认 MNN 配置：`http://127.0.0.1:8080/v1`、`mnn-local`、最大输出参数 `512`。模型实际加载和部分生成参数是否生效仍由 MNN 决定。

使用说明及构建方法见 [现有功能说明](mnn-group-summary.zh-CN.md)，测试入口见 [JVM 测试说明](../tests/ai-summary/README.md)。

## S1 用 Prompt 引导总结方向

在总结面板增加“总结方向”。首版提供模板和补充要求，保持现有“话题、结论、待办”三个栏目以及原文引用。Prompt 用于引导关注点，不替代客户端的消息读取范围。

### 用户可配置的内容

| 配置 | 首版方案 |
| --- | --- |
| 模板 | 通用总结、项目进展、决策与争议、待办跟进 |
| 补充要求 | 多行自由输入；空白表示不补充，可恢复默认 |
| 长度与语言 | 首版保持简洁中文；明确告知固定格式，暂不增加任意输出格式编辑器 |
| 保存范围 | 默认仅本次使用；用户可选择保存为该群／Topic 的偏好，或当前账号默认值 |
| 优先级 | 本次覆盖 → 当前群／Topic 偏好 → 当前账号默认 → 内置默认 |
| 长度限制 | 初始限制 1000 个 Unicode 字符，并计入请求预算；该数值待真机评测调整，超限明确提示 |

可直接使用的补充要求示例：

> 重点总结版本发布相关的进度、阻塞和已确认决定。待办列出明确的负责人和截止时间；没有明确提到的写“未指定”。压缩闲聊，保留不同意见及原消息引用。

> 重点整理数据库迁移方案的理由、反对意见和仍未解决的问题。区分建议与已经确认的方案，每项附原文依据。

“忽略闲聊”“关注某人”只改变模型总结的侧重点，所选范围内的文字仍可能发送给接口；真正排除消息由 S6 的客户端筛选完成。界面应把“消息范围”和“总结方向”分开展示。

### 实现任务

- [x] S1-1 定义不可变 `PromptOptions` 和任务配置快照，包含模板 ID、补充要求、模板版本与内置规则版本。接口地址、模型、密钥配置继续独立管理；旧配置迁移为通用模板和空补充要求。
- [x] S1-2 分层组装请求：内置事实与引用规则、用户模板与补充要求、明确分隔的消息数据／中间摘要。聊天中的指令和中间摘要中的指令始终作为数据处理，用户补充要求也不能覆盖事实和引用约束。
- [x] S1-3 在每个原始分块、每轮中间合并和最终合并中传入同一份总结方向。不能只修改最后一轮合并，否则之前的分块可能已经遗漏关注的信息。
- [x] S1-4 分块前为内置规则、补充要求、阶段说明和输出预留预算；首版使用保守字符预算并说明不是精确 token 数，精确程度在 S5 改进。要求过长或可用消息预算不足时，在请求前报错，不静默截断消息或用户要求。
- [x] S1-5 实现模板选择、编辑、恢复默认、有效配置提示及保存范围。配置按真实账号身份、群和 Topic 隔离；运行中编辑只影响下一次任务，退出账号清理其保存的偏好。
- [ ] S1-6 为单块、多块、至少两轮合并、特殊字符、超长输入、账号切换和运行中编辑加入回归测试；使用 S0 样例比较不同方向的输出效果。

主要改动：`AiSummaryPrompt`、`AiSummaryClient`、`AiSummarySettings`、`GroupSummarySheet`；可新增专用的 Prompt 配置类，避免继续把所有状态堆入接口配置。

验收：默认设置维持现有能力；同一批消息切换模板后关注点确实变化，但原文明确的事实、负责人和时间不被改写；每次请求都携带正确方向；引用不重新编号，每个分块及合并的引用只能来自其输入覆盖的来源集合，最终引用不能越出本次快照；预算和账号隔离测试通过。程序可验证引用结构，结论是否被引用支持仍需样例评测及人工抽查，不能仅凭加了系统规则就宣称消除了模型幻觉。

## S2 可见进度和流式输出

- [x] S2-1 定义统一任务状态：读取消息、总结分段、合并摘要、校验引用、完成、取消、失败。显示已读取条数、当前分段／总分段和已耗时；不知道总量时不显示虚假的百分比。
- [x] S2-2 先接入非流式阶段进度，让不支持流式的服务也获得反馈；保留目前的取消和生命周期保护。
- [ ] S2-3 增加 OpenAI SSE 文本流解析和开关，验证 MNN 实际协议。处理跨网络块的 UTF-8、多个事件、`delta.content`、结束标记、错误、截断、空输出及思考标签分段；只消费回答正文。
- [x] S2-4 单分块且无需合并时显示该次最终回答的流；多分块时优先展示进度，仅在最终合并阶段展示最终答案流，避免把中间摘要当完整结果。流式内容标记“生成中”，引用校验完成前不开放跳转。
- [x] S2-5 限制 UI 刷新频率，校验完整响应后一次性提交结果。断流保留“未完成”的可见状态，不推进增量游标、不写成功缓存；不自动重发整个大请求，提供明确的重试或切换普通模式入口。

主要改动：`AiSummaryClient` 回调与传输、`GroupSummarySheet`；必要时拆分独立传输解析器和任务状态类。

验收：普通和流式均覆盖成功、取消、切后台、账号变化、网络中断及超长响应；不重复显示字符，不把思考文本或半截引用作为最终答案；模型不支持流式时普通模式仍可用。记录首字延迟和总耗时，不能把流式展示等同于推理加速。

## S3 上次总结之后和未读消息

先做“上次总结之后”，再做“未读消息”。前者使用独立总结游标，后者使用 Telegram 的已读边界，两种状态不能混用。

- [x] S3-1 定义范围快照与覆盖记录：真实账号身份、群／Topic、范围类型、下界、固定上界、日期／时区、读取完整性、来源映射和本次配置版本。沿用原有受保护内容及媒体过滤规则。
- [x] S3-2 增量游标按账号、群和 Topic 保存。首次使用明确显示尚无起点，可使用最近 N 条完成初始化；之后只读取游标后的新文字消息。只在本次完整覆盖、模型成功、引用校验和结果记录保存成功后推进游标。
- [x] S3-3 取消、失败、截断、缺页、达到扫描上限或只有部分覆盖时均不推进。已有增量游标时，普通“最近 N 条／当日”和重做旧范围不自动移动它，避免越过中间未覆盖的消息。
- [x] S3-4 修改 Prompt 不重置消息游标，也不自动重算历史；界面说明新方向只影响下一次任务，提供“用当前方向重做上次范围”。重做不回退已有游标。已有结果收到源消息编辑或删除事件后标记过期；增量首版仅覆盖新增消息，不承诺追溯所有旧消息修改。
- [x] S3-5 在聊天被标记已读之前捕获进入聊天时的未读边界，并固定本次消息上界。无法取得可靠边界时禁用该范围并解释原因，不退化为最近 N 条却仍标称“未读”。总结请求本身继续不修改已读状态。
- [ ] S3-6 覆盖初次使用、无新消息、Topic 切换、推理中到达新消息、跨午夜、部分读取失败、账号槽位复用、程序中断和重启恢复。
- [x] S3-7 为大量积压提供“连续分批补齐”：从旧游标之后由早到晚确定一个有界的连续批次，每批完整成功后只提交该批末尾，再由用户继续下一批。主动选择的完整小批次与触及扫描上限的残缺结果必须区分，不能取最新一批越过旧消息，也不能因积压永久超限而无法继续。

主要改动：`SummaryHistoryLoader`、`ChatActivity`、任务结果及游标存储、`GroupSummarySheet`。范围端点以聊天内可靠的消息位置记录，不能仅用全局整数 ID 跨群比较。

实现说明：首次进入前读取已知已读边界，普通群取 Dialog 与当前已读位置的较新值；论坛群全部话题视图禁用未读，需进入具体 Topic。持久记录是范围、游标和摘要哈希，不存原文或摘要正文；进程重启后可按记录范围分批重新生成，原文可能已经变化。取消和记录提交按同一个锁确定先后，取消若晚于提交不回退已完成批次，返回时重新读取已保存状态。

验收：范围固定、增量不漏掉游标后的有效新消息、重跑不会错误跳过；结果与游标写入具备一致的提交和恢复机制；用户明确知道此前历史是否包含。加入“旧游标后有大量消息，但用户先单独总结最近 10 条”的用例，确保后续增量仍覆盖中间消息；超过单次上限的积压可以逐批完整补齐，中途取消后能从最后成功批次恢复。

## S4 原文预览和可核对的待办

- [x] S4-1 点击引用先展示原文、发言人和时间，提供“跳回群聊”；相邻消息优先使用已读取范围内的数据，额外读取时单独标明。引用预览不自动把新增内容发送给模型。
- [x] S4-2 打开预览和跳转前重新检查账号、群／Topic 和内容可用性。消息删除、权限变化或变成受保护内容时显示不可用，不展示旧缓存正文。
- [x] S4-3 明确区分事实、建议、已确认决定、争议和未决问题。待办展示事项、明确负责人、明确时间和依据；缺失字段写“未指定”，不根据昵称或上下文猜造指派。
- [x] S4-4 若需要结构化卡片，使用客户端可校验的数据结构并验证来源映射，不假设 MNN 支持 `response_format`／JSON Schema。解析失败时明确提示，可回退到已验证引用的普通文本显示。
- [x] S4-5 首版不加入任务提醒、同步或完成状态管理；后续增加时，将用户手动状态独立保存，重新生成摘要不能覆盖用户操作。

主要改动：`SummaryMessage`、来源记录、结果解析与 `GroupSummarySheet`。新增结构化信息仅保存实际来源能够支持的字段。

首版使用经过来源编号校验的普通文本，不新增 JSON 卡片、任务提醒或任务状态。预览只展示重新核验的被引用消息，未自动拉取相邻消息；点击跳转时再核验一次。已观察到的源编辑／删除及权限变化会使当前结果过期。核验若缺少完整的当前群权限元数据会明确失败，不回退旧原文；真实服务返回形态仍待手机验证。

验收：跨屏原消息可定位；删除、编辑和权限变化的预览行为正确；“有人建议周五发布”不会变成“已决定周五发布”，被否定或转交的任务不会仍指派给原负责人。存在有效引用只能证明可定位，不能替代事实核对。

## S5 手机性能和长聊天优化

- [x] S5-1 按实际模型可用上下文计算保守预算，计入系统规则、自定义要求、消息元数据、输出预留及追问预留。服务未提供 tokenizer 或模型身份时，允许用户设置档位，明确估算误差，不宣称字符数等于 token 数。
- [x] S5-2 优先保持回复关系、时间相邻讨论和话题边界；过长消息继续可拆分，并保持稳定来源编号。跨段必要重叠需要去重，不能重复计算待办或制造多次决定。
- [x] S5-3 对同一 MNN 接口限制为一个活动推理任务，合理处理不同群发起的请求；评估失败分段重试，限定重试次数，仅在输入与配置快照未变化时复用已完成分段。
- [x] S5-4 先做有容量限制的内存缓存。缓存键包含真实账号、群／Topic、来源内容版本及实际输入哈希、Prompt 内容与规则版本、模型／接口配置、生成参数和输出解析版本；不将 API Key 明文放入键或日志。
- [x] S5-5 `mnn-local` 是别名，MNN 可能在同一地址、同一次 Telegram 会话中切换真实模型；无法识别模型版本时，默认不在独立总结任务间自动复用已有摘要，只允许用户明确选择“查看已有结果”并标明生成时间。“重新生成”必须绕过对应摘要和分段缓存。已观察到的源消息编辑、删除、权限变化使相应缓存失效；跨会话持久缓存另行设计有效性核验和加密清理，不直接作为首版默认。
- [ ] S5-6 使用 S0 同一设备和样例比较改动前后延迟、请求数、错误率、内存和温升，并复核结论、待办和来源支持关系。性能优化不得以隐藏截断或明显遗漏信息为代价。

主要改动：预算与分块策略、任务调度、来源版本及有界缓存；避免把所有逻辑塞进 HTTP 客户端。

首版预算可设 2048–32000 字符，默认 6000，按输出 token 参数乘 4 估算输出预留；这是可配置的字符估算，不是已知模型的精确 token 限额。没有真实 tokenizer 或模型版本时不能保证服务接受该请求，超限须调低输入或按模型实际情况配置。端点已有任务时明确拒绝新任务，不排队、不自动重试或复用失败分段；输入不变的手动重试由用户发起。取消完成连接清理后释放客户端占用，服务端是否仍在推理另行测量。

验收：改 Prompt、参数、账号、消息内容或可识别的真实模型后不会错误命中缓存；无法核实的缓存不能标称最新结果；离开账号后清理所属缓存。提交同一设备的对比数据和质量回归结果，依据测量决定是否启用优化。

## S6 与我相关和客户端筛选

- [ ] S6-1 在 `SummaryMessage` 和加载层补充真实发送者 ID、明确提及和回复关系等必要元数据；当前仅有显示名和正文，不能据此可靠识别“我”。
- [ ] S6-2 增加“与我相关”视图，优先展示明确 @我、回复我、原文明确指派给我的任务；不能把没有 @我解释为整段讨论与我无关。
- [ ] S6-3 将“突出与我相关的内容”和“只读取／发送符合条件的内容”作为不同选项。后者先在客户端筛选，并明确显示实际覆盖范围和为了理解而包含的上下文。首版的筛选任务不推进通用增量游标，避免切回全部消息时跳过此前被排除的内容；如以后需要筛选增量，应另建包含筛选规则版本的独立游标。
- [ ] S6-4 按需要增加指定成员／关键词筛选；先定义身份匹配、大小写及关键词规则，再实现，避免让模型承担确定性的筛选。

验收：同名成员和修改昵称不混淆身份；回复关系缺失时不猜测；关注点模式不伪称已排除其他消息，筛选模式确实遵守输入范围并保留必要来源说明。

## S7 围绕本次消息追问

- [ ] S7-1 在结果页提供追问输入及“为什么这样决定”“还有哪些分歧”“谁负责跟进”等入口。
- [ ] S7-2 首版限于本次有效消息快照及可定位的原文依据；摘要只作辅助信息，不能单独充当新结论的事实来源。用户问题本身也不是群聊事实。
- [ ] S7-3 按预算从本次消息中取证，并提供明确的范围和上下文不足提示；不自动扩展为全群历史搜索。需要更多消息时由用户重新选择范围。
- [ ] S7-4 限制追问轮数、历史输入量和输出量，暂以最多 5 轮为初始配置，具体预算经真机验证再确定。更换账号、群、范围或 Prompt 后建立新会话，不混入上一任务的回答。
- [ ] S7-5 保留普通／流式选择、取消和引用验证；追问不会推进总结游标，不生成无依据的待办，也不自动向群发消息。

验收：范围外问题明确说明依据不足；相同来源下的摘要与回答不自相矛盾，新增事实陈述都有可核查引用；达到预算上限时明确停止而非静默遗忘关键上下文。

## 后续候选和暂缓范围

全天后台自动总结、跨群长期记忆、大范围历史检索、图片／语音理解、外部任务同步和自动发送群消息暂不进入以上四轮。它们会显著增加耗电、上下文管理或外部操作复杂度，应在文本总结的速度和质量有实际数据后单独规划。

正式发行前另行处理长期私有签名、自有 Telegram API 配置及相关发行配置。当前 CI 调试密钥依赖缓存，不能作为可靠的长期升级签名；缓存失效可能产生签名冲突，不应让用户通过反复卸载来承担正式版升级成本。Actions 依赖版本升级作为构建维护项验证，不与摘要功能混为一项验收。
