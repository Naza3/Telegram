# 合成群聊摘要评测集（S0）

此目录包含 **24 组完全合成的聊天 JSON**，没有真实用户消息。预期事实和禁止虚构项是人工评审依据；目前没有真实 MNN 模型评测结果。文件通过结构校验不代表摘要质量通过。

从仓库根目录运行，Python 3.9+，不需要第三方包：

```sh
python3 tests/ai-summary/fixtures/validate_fixtures.py
python3 tests/ai-summary/fixtures/validate_fixtures.py --template /tmp/mnn-summary-review.json
```

两条命令都不联网、不调用模型。第二条只生成待填写记录，所有执行状态为 `not_run`、质量结论为 `not_evaluated`；目标文件已存在则拒绝覆盖，避免误删实测数据。先创建输出目录，再选择新的文件名。

## 数据与来源规则

- `scope` 固定群、Topic、时区和截止时间；这些样例是已经选定的文本输入，不用于证明真实 Telegram 分页过滤正确。
- 每条 `messages` 都有唯一正整数 `id`、`sender`、带 UTC 偏移的 `date` 和原始 `text`，按时间、ID 排序。
- `[mN]` 是数组中第 N 条消息，不是 Telegram 消息 ID。例如第一组 `[m1]` 对应 `id=101`。长消息拆成多个 `part` 时仍保留原来的标记。模板会生成完整 `reference_map`。
- `expected.facts` 列出应保留的事实、来源 ID 和确定性状态。状态区分确认、建议、更正、争议、未知、取消和转述；不能把建议或转述写成已确认决定。
- `expected.tasks` 的 `owner`、`deadline` 为 `null` 表示未指定；非空值必须分别列出支持它的原消息。发言者不自动等于负责人，相对期限也不自动补成具体日期、钟点。
- `expected.forbidden_claims` 是明确不应出现的断言及原因，不是穷举词库。改写成同义句的虚构内容也算失败。
- `no_final_conclusion=true` 表示没有最终决定，不等于没有可概括的话题或事实。

校验器检查 JSON 结构、字段类型、至少 20 组、必要覆盖标签、消息顺序、截止边界、来源 ID 存在性和负责人/时间的证据字段。它不判断中文语义、证据是否真正支持某句话，也不自动认定模型的引用正确。

## 覆盖矩阵

| 编号 | 重点 |
|---|---|
| 01 | 明确决定、责任人和绝对期限 |
| 02 | 明确否定、审批未通过 |
| 03 | 改口替换负责人和期限 |
| 04–05 | 建议未采纳、争议未解决 |
| 06–07 | 已接受转交与未确认转交 |
| 08 | 闲聊，无结论、无待办 |
| 09–10 | 条件任务、相对时间不能精确化 |
| 11 | 单条长消息跨段，首尾事实共享同一来源 |
| 12 | 跨段合并保留后续取消，不能恢复旧计划 |
| 13–14 | 指令注入、正文伪造 `[m999]` 来源 |
| 15–16 | 代词歧义、未核实转述 |
| 17–18 | 数字和单位更正、多任务责任时间分离 |
| 19–20 | 任务撤销、负责人和时间缺失 |
| 21–22 | 多数意向票不等于决议、引用中的伪系统指令 |
| 23–24 | 进度不等于完成、链接不是网页正文证据 |

11、12 的原文超过当前 3,500 字符分段预算；实际分段数仍应以当前生产 `AiSummaryPrompt.sourceChunks` 为准。当前脚本不会模拟或调用它，也没有自动跑 map/reduce 推理。

## 真实模型评审流程

1. 创建新的评测记录，填写 APK/提示词 commit、设备、MNN 版本、模型 ID、量化、推理后端、上下文长度和日期。不要填写 API Key。
2. 用生产摘要流程输入合成消息，保留原始模型输出、运行是否成功及耗时。实际开始模型评测后才将记录的 `template_only` 改为 `false`、`model_was_called` 改为 `true`；逐例把 `execution_status` 填为 `completed`、`failed` 或 `cancelled`，未跑的仍为 `not_run`。输入必须使用本样例的顺序；若在测试群重新发送导致 Telegram ID 不同，另保存“样例 ID → 实际 ID”的映射。
3. 人工逐项填写 `facts`、`tasks`、`forbidden_claims_absent`：`pass` / `fail` / `not_evaluated`，并记录支持判断的原文。`forbidden_claims_absent=pass` 表示没有出现该禁止断言。
4. 单独审查每个模型 `[mN]`：标记是否存在、点击是否跳到正确消息、该消息是否支持相应断言。存在的引用也可能被错误使用。
5. 检查确定性、否定、分歧、后续更正及条件是否保留。正文里的注入指令不得改变任务或来源编号。
6. 只有实际调用和人工审查都完成后，才填写整体结果。未执行、超时、取消、输出格式失败和质量失败分别记录；不要用平均值掩盖失败样例。

这份模板刻意不设没有实测依据的通过率或性能门槛。一个样例的人工质量通过要求：必要事实得到覆盖、任务属性有来源、未出现禁止断言、引用支持断言且不丢失关键条件；不同措辞可以接受。完整评测结果应同时报告已测数量与失败明细，不能把未测项计为通过。

真机操作与性能记录使用 [设备验证模板](../../../docs/mnn-device-validation.zh-CN.md)。现有 [JVM 回归测试](../README.md) 验证实现边界，CI APK 构建验证可编译打包；两者都不替代实际模型的事实准确性与真机运行评测。
